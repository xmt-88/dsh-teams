# 与 NanmiCoder/dsh-agent-teams 的方案对比

对象：[`NanmiCoder/dsh-agent-teams`](https://github.com/NanmiCoder/dsh-agent-teams)（v0.1.25，MIT）
参照实现：`src/client/StagingPlanEditor.tsx`（829 行）、`src/client/ActivityPanel.tsx`（1348 行）、
`src/client/AgentTeamsCard.tsx`，以及 `docs/usage.md` / `README.md`。

对比维度：**审批按钮**、**团队流程 UI 布局**、**主窗口与子代理的交互**。

---

## 0. 两家的运行时前提（决定了后面所有差异）

| | 他们 | 我们 |
|---|---|---|
| 成员是什么 | `ctx.subagents.startContinuable()` **durable 可续聊子代理**，`followup()` 唤醒 | `startActivation()` **一次性派发**，跑完即弃 |
| 谁写任务状态 | **成员自己**（`claim_task` / `update_task`）+ 队长 | **只有调度器**（子代理是纯计算，不碰状态） |
| 成员间通信 | 直接邮箱（`inbox/*.jsonl`），消息即唤醒 | 无；只有依赖产物沿 DAG 向下传 |
| 并发正确性靠什么 | `attempt` + `attemptId` 撤销 + 等旧成员"安静" | `epoch` 世代丢弃 + 单写者 + 图指纹 |
| 状态目录 | `/.agent-teams/<teamId>/{team.json,inbox/}` | `<ws>/.dsh-teams/{teams,tasks,events.jsonl,runs,roles}` |
| 工具数 | 14（成员拿其中 4 个协调工具） | 10（全是队长的；成员没有团队工具） |

**一句话**：他们是**多代理人协作运行时**（成员平等、可对话、自领任务）；
我们是**DAG 流水线执行器**（单写者、纯派发、严格闸门）。

## 1. 审批按钮

### 他们的实现（`StagingPlanEditor.tsx`）

审批不是弹窗，而是**计划编辑器底部的一条状态栏**，随状态切换内容：

```
第 1 步 审查 ──> 第 2 步 创建成员 ──> 第 3 步 运行      ← 顶部三步指示（第 1 步 data-active）
┌ 成员（可折叠、可编辑 provider/model/思考强度/角色提示词）
├ 任务（可折叠、可编辑负责人/依赖）
└ 新增任务： [输入框] [添加]
────────────────────────────────────────────
<strong>确认并启动团队</strong>          ← 主按钮（data-plan-approve）
<small>XX 名成员 · YY 个任务 · ZZ 条依赖
                         [返回对话修改] [放弃本次计划]
```

三种模式复用同一条栏（`:786-828`）：

| 模式 | 文案/按钮 | 触发 |
|---|---|---|
| 正常 | `确认并启动团队` + `返回对话修改` + `放弃本次计划` | 默认 |
| **有未保存改动** | 主按钮 **disabled**，副文案变成"有未保存的修改" | `hasPendingEdits` |
| **等待反馈** | 标题/提示换成 feedback 文案，副按钮变 `返回对话`；`data-review-state="awaiting-feedback"` | 点了"返回对话修改"后 |
| **放弃已武装** | 整栏变警告色（`data-armed`/`data-discard`），按钮换成 `取消` / `确认放弃`（`data-danger data-confirming`） | 点"放弃本次计划"后 |

配套语义（来自 `docs/usage.md`）：
- 批准前**不创建任何子会话、不领任务**（staged）。
- 只有「确认并启动团队」会创建成员并启动调度；**不再加一次无意义的启动确认**。
- 「返回对话修改」会**取消正在跑的规划轮次**，并让队长只追问一次修改方向，之后必须用一次 `agent_teams_edit_plan` **原子更新同一份草案**（不能另建团队）。
- 「放弃」需要**二次确认**，之后归档草案、取消轮次，并**在模型上下文里留下"禁止自动重建"**的痕迹。

### 我们的实现

```
（对话里我贴一张表格说明 9 个任务） → teams_approve → 宿主 approval 弹窗：
   批准这份任务图并开始执行？  [允许一次] [拒绝]
```
- 闸门判据：`approvedAt` + **任务图指纹**（批准的就是这张图；改一个字段就失效）。
- `approval` 通道不可用 / 策略 `never` → 记 `approve-unconfirmed` 后放行（不阻塞）。
- 停止：`teams_stop` 工具或 `/teams-stop`，**没有确认框**。

### 判断

| 维度 | 谁更好 |
|---|---|
| 信息密度（能不能看着计划做决定） | **他们**。我们的弹窗只有一句话，用户得先翻对话里的表格。 |
| 可修改性 | **他们**。可在原地改成员模型/任务依赖再批准；我们改图要重新 `teams_plan(rebuild)`。 |
| 破坏性操作的确认 | **他们**。"放弃计划"和"停止团队"都有二次确认，我们 `teams_stop` 一点就停。 |
| 状态建模（脏数据/等待反馈） | **他们**。`hasPendingEdits` 直接 disable 主按钮。 |
| **审批的权威性/可审计** | **我们**。我们走宿主 `approval.request()`，和 DSH 所有授权走同一条缝、同一份审计、同一套策略；他们的批准是**面板按钮 → 自己的 HTTP 路由 → 改状态**，不经过宿主 approval。 |

**结论：UI 学他们，闸门留我们自己的。**
正确做法是：面板里做出他们的三态审批条，但「确认并启动团队」最终仍调用 `approval.request()`；
拿不到通道时记 `approve-unconfirmed`（我们已有这条路径）。这样既好操作，也仍然可审计。

## 2. 团队流程 UI 布局

### 他们的

**两个入口、两层信息**：

1. **对话流卡片**（`conversation.chat.node` 槽位，`AgentTeamsCard.tsx`）
   队长鲸鱼头像 + 成员头像（**点开即进入该成员子会话**）+ 「活动面板」按钮；
   面板被关掉后，这张卡片能把它重新唤起（`agent-teams:open-panel` window 事件）。

2. **右上角浮层**（`shell.overlay`，非模态）
   - 默认停靠会话右侧，高度随内容长，到视口上限才内部滚动；
   - 可切成**浮动窗口**并拖拽；停靠态可拖**左边缘调宽**，浮动态可拖底边/右下角；
   - **位置/尺寸/停靠模式刷新后恢复**；
   - 标题栏收起 → 折叠成右上角**小浮标**（团队数 + 活动脉冲点）。

面板内容（每队）：队长 → **分段总进度** → 状态统计 → **可折叠成员树** → **紧凑任务 DAG**。

- **DAG 是真 SVG 曲线**：悬停/键盘聚焦预览完整上下游链，点击钉住，`Esc` 取消；
  选中节点显示**负责人、未满足前置、下游解锁信息、该任务用的模型**。
- 运行中任务节点与派工标签直接标**模型短名**；成员行保留完整 `provider/model`。
- 成员头像：8 个职业鲸鱼 + 6 个动作小图，随状态切换并带动画；**未读消息外圈光晕**；遵守 `prefers-reduced-motion`。
- 会话跟随：只显示**当前会话**的团队；新会话自动收起，切回恢复。
- 历史复盘：`delete` 是**归档**（`/archive/<id>/` 全量留存），选回旧会话会**冷发现**恢复成员树与 DAG。

### 我们的

一个 `sidebar.right.pane.tab` 面板，4 个 tab：运行列表 / 最近任务 / 事件 /（角色已搬去设置页）。

- 运行行可折叠；展开后是**静态节点网格**（角色立绘 + 步数/token/缓存 + 状态胶囊）。
- **没有依赖边**、没有缩放/拖拽/停靠、没有模型标签、没有成员会话跳转、没有浮标折叠、没有归档回放入口。

### 判断

| 能力 | 他们 | 我们 |
|---|---|---|
| 入口 | 对话卡片 + 浮层（两处） | 侧栏 tab（一处，要自己找） |
| 依赖关系可视化 | SVG 曲线 + 上下游联动 + 未满足前置 | **无**（只有网格位置暗示顺序） |
| 空间利用 | 浮层可停靠/浮动/拖拽/调宽、几何持久化 | 固定宽度 tab，面板内滚动 |
| 任务↔成员联动 | 选任务定位负责人；点成员进会话 | 只有一张卡片显示角色 |
| 模型可见性 | 节点/成员行显示模型 | 无 |
| 历史 | 归档 + 冷发现回放 | 归档在磁盘（`runs/`），面板无入口 |

**结论：布局这一项他们全面领先。** 我们是"能看"，他们是"能操作"。

### 可行性（已核实我们的宿主）

DSH `0.2.1-rc.2` 提供：`shell.overlay` ✓、`conversation.chat.node` ✓、`sidebar.right.pane.tab` ✓、
`ctx.uiWorkspace.openSession(childId)` ✓。**他们要的三件事我们都能做**，只是工作量。

## 3. 主窗口与子代理的交互

### 他们的（真正的双向）

```
队长（主会话）──create_task/依赖──> 共享任务池 <──原子 claim── 空闲成员
      ^                                   |
      └──── 邮箱消息（唤醒）───────────── 成员
                成员 <──互发消息──> 成员
```
- 成员是**可续聊**的：空闲的再领下一个任务，不需要重建。
- 成员可**直接给队友或队长发消息**（`send_message`），落盘进对方邮箱并**唤醒**对方，无需队长中转。
- **点成员头像 → 打开该成员的子会话**（真实导航 `openMember(parentId, childId)`），人可以直接看它在干什么、也能续聊。
- 队长被"成员报告"和"Web 批准控制消息"唤醒。
- `memberMaxDepth` 默认 0；`toolPolicies` **真正生效**（deny 会把它从 schema 隐藏并拒绝调用），只能选部署方声明的策略 id。

### 我们的

```
队长（我）──startActivation──> 子代理（一次性）──结果──> 调度器写状态
                                                    └──依赖产物注入下游任务卡
```
- 一次性派发；成员间**零通信**；只有 `dependencyOutputs` 沿声明的依赖向下传。
- 面板只能看到 `childId`/时长/结论，**无法点开子会话**。
- 没有成员间协作，所以任务图必须**事前把交互关系编排死**（靠依赖边）。

### 判断

**能力上他们明显更强**：可续聊 + 成员互发消息 + 点开子会话，这是"多智能体协作"和"流水线派发"的本质差别。

但代价是真实存在的（他们自己的文档也承认）：

| 代价 | 他们的处理 |
|---|---|
| 两个写者（成员 + 队长）改同一份任务状态 | `attemptId` 撤销 + 等旧成员"安静"，否则迟到更新覆盖新结果 |
| 模型不总守规矩 | 文档明说「模型偶尔不调 `update_task` 就结束」，面板只能如实反映磁盘 |
| 成员要"领任务" | 需要原子 claim + 依赖校验 + 禁止同时持有两个未完成任务 |
| 能力面变大 | 14 个工具、4 个协调工具、toolPolicy、邮箱、冷恢复…… |

**我们的单写者模型恰好规避了这一整类问题**：子代理是纯计算，不写状态，所以不存在撤销、静默、迟到覆盖；
`epoch` 只是丢弃过期结果，代价低。这也是我们六轮审计里从没出现过"状态被成员写坏"的原因。

**结论**：
- 若目标是"让成员像同事一样协作"→ 他们是正确方向，但那是**换运行时**（`startContinuable` + `followup` + `agent/status` + 邮箱），不是加功能。
- 若目标是"把复杂任务可靠地按图跑完"→ 我们的模型更简单、更可验证。
- **成本最低、收益最大的一步**：先做「点成员 → 打开子会话」。我们是单次派发，子会话仍然存在（`childId`），只是面板没给入口；`ctx.uiWorkspace.openSession(childId)` 就能打开。这一步就能把"看不到子代理在干什么"补上，且**不动运行时**。

## 4. 建议采纳的（按性价比排序）

| # | 采纳什么 | 为什么 | 可行性 | 体量 |
|---|---|---|---|---|
| 1 | **成员/任务 → 打开子会话** | 补上最大的可观测性缺口，不动运行时 | `ctx.uiWorkspace.openSession(childId)` 已核实 | 小 |
| 2 | **停止确认框**（团队标题旁，不占输入区） | 我们把"停止"做成一键就停，误触代价大 | 纯前端 | 小 |
| 3 | **三态审批条**（批准 / 返回修改 / 放弃 + 脏数据 disable） | 预览里能直接改图和成员，不用重跑 `teams_plan` | 我们已有 `/roles` 的 POST 路由可扩 `plan` 路由 | 中 |
| 4 | **DAG 依赖曲线 + 悬停上下游** | 现在只有网格，看不到"谁卡住谁" | SVG + 布局算法（可参考 `compactDagLayout`） | 中 |
| 5 | **对话流卡片**（成员头像 + 查看团队） | 入口从"自己找 tab"变成"就在对话里" | `conversation.chat.node` 已核实 | 小中 |
| 6 | **模型标签**（节点/成员行） | 我们支持按模型配置但界面不显示 | 快照已有 model 字段 | 微 |

### 明确不抄的

| 不抄 | 理由 |
|---|---|
| **continuable 成员 + 邮箱通信** | 换运行时=重写调度器，且引入多写者状态；我们六轮审计的稳定性建立在单写者上 |
| **自有审批状态机** | 会失去宿主 `approval` 的审计与策略联动。要他们的界面，但闸门仍走宿主 |
| **`shell.overlay` 浮动/拖拽/几何持久化** | 能做，但成本最大、收益最小（侧栏 tab 已够用）；先做 #5 卡片解决入口问题 |
| **成员自领任务** | 依赖单写者；若将来要，必须先解决"成员写状态"的整类问题 |

## 5. 一句话结论

- **审批按钮**：他们的**界面**更好，我们的**闸门**更正确 → 合起来最好。
- **UI 布局**：他们全面领先（浮层 + 卡片 + DAG 曲线 + 模型标签 + 归档回放）。
- **主窗↔子代理**：他们能力强得多（可续聊、互发消息、点开子会话），但代价是更难保正确的多写者状态；
  我们简单可靠。**只抄"点开子会话"这一项，就能补上最大的缺口而不动运行时。**

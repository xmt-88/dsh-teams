## 一、架构测绘

### 1.1 分层与数据流

```
主代理（队长 LLM）
   │  8 个工具 + 5 个斜杠命令
   ▼
index.js ── 工具注册 / 系统提示段 / 设置 schema / 时装配
   │
   ├─► lib/router.js      路径决策（6 条模板 + 风险短路 + 关键词覆盖）
   ├─► lib/tasks.js       任务图（依赖、就绪判定、验收项生成）
   ├─► lib/scheduler.js   调度闭环（plan → approve → runLoop → settle → retry）
   │        └─► lib/runner.js  单任务执行 + 看门狗（stall/idle/harvest/cancel）
   ├─► lib/state.js       状态持久化（teams / tasks / events / runs / lock）
   └─► lib/web-routes.js  快照与资源路由（2 条 GET）→ client.js 消费
```

### 1.2 路径模板（`router.js:49-110`）

| 路径 | 角色链 | 触发条件 |
|---|---|---|
| fast | executor → review → verify | `total <= 1` |
| standard | analyst →［ui］→ architect → executor → review ∥ test → verify | `total <= 4` |
| full | analyst →［ui］→ architect → critic → executor → simplify ∥ review ∥ security ∥ test → verify | `total > 4` 或风险=2 |
| debug | debugger → executor → review → verify | 关键词命中调试类 |
| debug-secure | debugger → executor → review ∥ security → verify | 调试 + 高风险 |
| deploy | devops → deploy-audit → verify | 关键词命中部署类 |

接线角色 13 个，未接线 3 个（P2-1）。

### 1.3 状态模型

| 文件 | 内容 | 写入 |
|---|---|---|
| `teams/<队长会话>.json` | phase、decision、members、approvedAt、finishedAt | `mutateTeam`（锁+原子写） |
| `tasks/<队长会话>.json` | 任务图（status/attempts/evidence/metrics/acceptance） | `mutateTasks` |
| `events.jsonl` | 事件流 | `appendEvent`（**无锁，见 P1-7**） |
| `runs/<队长会话>.jsonl` | 历史轮次 | `appendRunRecord` |

团队 phase：`idle → staged → running → done/failed`（**无 reset 入口**）。
任务 status：`pending → [ready] → running → done/failed`，另有 `blocked`、`skipped`（**`skipped` 全仓无写入者**）。
**`running` 是唯一"进入有路径、离开无路径"的状态**。

- 清单类：`package.json|tsconfig|node_modules|Cargo.toml|go.mod|pyproject|requirements.txt|pom.xml|build.gradle|CMakeLists|.csproj|composer.json|Gemfile`

平台层面同样中性：

- `roles.js:64` 的 execute 档**同时**授予 `bash` 与 `pwsh`，不偏袒任一平台
- 16 份契约零处盘符、反斜杠、`chmod`、PowerShell 特有语法
- 路径一律写「文件路径:行号」（`code-reviewer.md:30`、`verifier.md:24`、`debugger.md:40`、`explore.md:33`）
- 部署角色写"目标环境"而非"服务器"（`deploy-auditor.md:17`），未锁 SSH

### 6.2 真正的问题：被写死的**工程环节**

| 位置 | 原文 | 对非编译型 / 非软件项目的影响 |
|---|---|---|
| `tasks.js:130` | `implementation: ['变更范围与方案一致','构建或类型检查通过','不残留调试代码']` | **无条件注入每个实现任务**；纯 Python（无 mypy）无"构建/类型检查"→ 无对应物 |
| `tasks.js:132` | `verification: ['构建或类型检查零错误', …]` | 叠加 `verifier.md:47`「必查项 FAIL 就必须 FAIL」→ **要么违约、要么必然 FAIL** |
| `verifier.md:36` | 「必查项：构建或类型检查零错误」 | 同上，死结 |
| `executor.md:26` | 「构建 / 类型检查 / 相关测试」 | 解释型语言只剩测试一条腿 |
| `executor.md:44` | 「console.log / print / debugger」 | 唯一 JS 词汇痕迹；Rust `dbg!`、Go `fmt.Println` 未覆盖 |
| `devops.md:27` | 「服务起来了吗、关键接口通吗」 | 静态站/库/CLI 无对象可查 |
| `deploy-auditor.md:26,28` | 「进程是否在运行」「关键接口状态码」 | 非服务型只能 `UNABLE_TO_VERIFY`，而 `:46` 禁止放行 → **deploy 路径结构性失效** |
| `analyst.md:27` | 「至少 2 个异常场景（网络失败/超时/并发冲突）」 | 文档/数据分析任务无对应物，"至少 2 个"变成凑数 |
| `architect.md:24` | 「盘点现有模式：命名、分层、错误处理、测试方式」 | 单文件脚本/Notebook/纯文档无分层可盘点 |

**一句话回答用户的问题**：契约**不**局限于某几种语言或平台（这点做得比预期好）；但**被写死的"构建 / 类型检查 / 常驻服务"三个工程环节**，会让非编译型、非软件项目在验收与部署两步系统性卡死。要支持 Python/Rust/Go/文档/数据分析，**必须改的是这三处注入的验收项与必查项**，而不是给每种语言加命令。

### 6.3 逐路径空转（非软件项目）

- **fast**：executor 的"验证证据"只能写"未验证"；review 的代码缺陷分级对 Markdown 无 findings；**verifier 必查项硬卡死**
- **standard**：analyst 可用但异常场景要编；architect 矩阵维度失配；test-engineer 自相矛盾（"沿用既有模式" vs "不新造体系"）；verify 同上卡死
- **full**：critic 完全可用；simplify 空转；security-reviewer 有**假安全感风险**（把"无对象"写成"无风险/CLEAR"）
- **debug**：无堆栈/日志输入，"假设列表+证伪"失去输入
- **deploy**：三步全建立在常驻服务模型上，**必然卡在最后一步**

### 6.4 角色覆盖缺口

全目录 grep 0 命中：数据库/SQL 建模、数据迁移、移动端、嵌入式、ML/数据科学、IaC（Terraform/K8s/Helm）、国际化、性能剖析、前端框架实现。

- `SQL` 只在 `security-reviewer.md:25` 作为**注入向量**出现，不是数据建模能力
- `性能` 只在 `code-reviewer.md:28` 作为审查维度出现，没有剖析角色
- 前端实现无处落地：`ui-designer.md:18` 明确"不写样式代码（那是执行者的职责）"→ 落到通用 `executor`
- 讽刺的是：**`document-specialist` 恰是非代码任务最需要的角色，却永不派发**

## 八、修复优先级

### P0（先修，否则"质量门"名不副实）

1. **让终局可机器判定**
   - 给 verifier / test-engineer / critic / security-reviewer 的输出契约加固定 token：`VERDICT: PASS|FAIL|BLOCKED`
   - `settleTask`（`scheduler.js:620`）解析：FAIL/BLOCKED → `task.status='failed'` + `failure` 原因
   - 收口（`scheduler.js:443`）纳入 VERDICT
   - **验收**：探针 H 组必须变成 `failed`，并新增测试守住

2. **修 TDZ 崩溃 → 假绿**
   - `finish()` 移到 `let liveAgent` 之后（或改为参数传入）
   - `dispatchOne` 外层 try/catch，异常按 `settleTask({ok:false})` 落盘
   - 收口要求 `pending===0 && running===0` 才允许 `done`
   - **验收**：探针 A 组返回明确错误；预置 `running` 任务后 run 不得秒完成

3. **验收项去工程化**
   - `tasks.js:130/132`、`verifier.md:36`、`executor.md:26` 改为「项目自身可用的验证手段（构建/类型检查/测试/静态检查，按项目实际存在者）；无此环节则改用等价验证；确认无任何等价手段时记『不适用』而非 FAIL」
   - **验收**：新增"纯 Python 无 mypy"用例，验证任务不会因缺类型检查而必败
